## Decision

The Project owner approves preserving the current implemented B2A2B2-owned
provider/payment input rules, opaque-token rules, retained repair rules, and
source-derived game-credit safeguards listed below.

This approval is limited to current reachable behavior that already exists in
the accepted source tree and remains compatible with current supported callers.
It does not approve unrelated current schema constraints merely because they
exist.

The limits and thresholds register may record the approved values selected
here, but this decision record is the approving source.

## Approved B2A2B2 Rules

| Request family / field | Exact approved rule | Enforcement layer | Protected behavior/resource | Current caller compatibility | Ownership boundary / handoff |
|---|---|---|---|---|---|
| Saved payment-method sync `setup_intent_id` | Required when `POST /user-payment-methods/sync` is used; surrounding whitespace is trimmed; blank input rejects; maximum length is 255 characters; value is treated as an opaque provider identifier; Stripe prefix format is not used as local legitimacy proof. | Request schema plus payment-method service provider validation. | Prevents blank or oversized provider identifiers from reaching the saved-card sync workflow while preserving provider authority for real SetupIntent facts. | Current frontend saved-card setup sends the SetupIntent ID returned by the Stripe setup flow. | Provider-backed service validation remains authoritative for SetupIntent existence, ownership, status, customer association, and PaymentMethod legitimacy. WS05 owns provider/runtime evidence. |
| Inbox global-seen `seen_token` | Required when `PUT /inbox/app-updates/global-seen` is used; surrounding whitespace is trimmed; blank input rejects; maximum length is 512 characters; request schema treats the value as an opaque server-issued token. | Request schema plus inbox service signed-token validation. | Prevents blank or oversized inbox tokens from reaching global-seen mutation while keeping token semantics server-owned. | Current inbox frontend sends the server-issued global-seen token from the inbox response. | Inbox service owns signature, kind, version, user, sequence, and payload validation. EN-03 owns `INBOX_TOKEN_SECRET` independence and broader secret lifecycle. The 512-character limit is an application input bound with headroom, not a universal token-format maximum. |
| Checkout payment-intent `return_url` | Optional; when supplied, surrounding whitespace is trimmed; URL must be absolute `http` or `https`; embedded username/password credentials, query strings, and fragments reject; origin must exactly match a configured Pickup Lane application/CORS origin; path must be exactly `/games/{game_id}/checkout`; external origins and alternate paths reject; temporary deployment hostnames are not hard-coded. | Checkout service validation before game lookup, database mutation, or provider work. | Prevents arbitrary redirect targets or parameter-bearing URLs from becoming provider return destinations for checkout. | Current checkout frontend supplies the active browser game checkout URL. | Broader production HTTPS, canonical-domain, edge, URL-size, process-server, deployment-host, and provider-precedence policy remains with its existing owners. |
| Generic payment/refund/event mutation retirement | Generic `POST /payments`, `PATCH /payments/{payment_id}`, `POST /refunds`, `PATCH /refunds/{refund_id}`, and `POST /payment-events` remain unavailable as generic write surfaces. | Route lifecycle tombstones and current active workflow routing. | Prevents generic CRUD-style request bodies from writing payment, refund, or raw payment-event state. | No current production frontend caller depends on these generic mutation surfaces. | Supported writes remain owned by checkout, signed webhook processing, admin-money workflows, refund/retry/reconcile workflows, official-game workflows, and later WS05 payment/provider lifecycle work. |
| Payment-event repair input | Retained repair route request-writable fields are limited to `payment_id`, `processing_status`, and `processing_error`; optional `processing_error` is trimmed; maximum length is 1000 characters. | Payment-event update schema plus payment-event service preservation of provider-owned fields. | Allows narrow operational repair without letting request bodies rewrite provider event identity or raw provider facts. | Current source has no production frontend caller for provider event creation; repair remains an admin/backend surface. | Provider identity, provider event ID, event type, raw provider payload, provider timestamps, and other provider-owned metadata are not request-writable through the repair surface. Signed provider webhook/API inputs and WS05 evidence remain authoritative for provider facts. |
| Game-credit issue/reverse operational text | Issue and reverse `idempotency_key` are optional, trimmed, and capped at 160 characters. Issue and reverse `note` are optional, trimmed, and capped at 1000 characters. Blank optional operational text may normalize to absent/null at the service layer. | Game-credit request schemas plus service normalization. | Keeps admin operational identifiers and notes finite without inheriting unrelated A2A request-family values. | Current admin/backend game-credit routes can use short operational text and idempotency keys. | These values are B2A2B2-specific. They do not approve a general idempotency policy for other routes. |
| Game-credit source-derived issuance eligibility | Generic admin game-credit issuance must have a source booking and/or source payment that supplies server-owned monetary eligibility. `source_game_id` may establish or confirm official in-app game context but does not by itself provide a monetary ceiling. Supplied or derived source booking/payment/game references must belong to the credited user and agree with one another. Eligible source games must be official in-app games. The monetary ceiling is the minimum applicable server-owned booking/payment amount from the validated source context. Existing non-reversed credits for the credited user sharing the relevant source reduce remaining eligible amount. Requested credit must be positive and no more than remaining eligible amount. No universal monetary ceiling is introduced. Source-less discretionary issuance remains disabled. Reversal remains bounded by the existing credit record and current eligible unused amount; no client-supplied reversal amount is introduced. | Game-credit request schemas plus PostgreSQL-backed game-credit admin service validation. | Prevents generic admin credit requests from fabricating source-less or excessive monetary value. | No current frontend caller depended on source-less discretionary issuance at inspection time. | Any future source-less discretionary credit capability requires a separate owner decision defining authorization, monetary limits, audit semantics, idempotency, and operational safeguards. WS05 owns broader payment/refund/credit lifecycle and reconciliation evidence. |

## Evidence Boundary

This decision approves current source-owned request rules only. It does not
claim provider dashboards, deployed runtime behavior, external staging behavior,
payment-provider lifecycle correctness, durable reconciliation, multi-instance
concurrency closure, telemetry dashboards, alert thresholds, or full PAY control
closure.

## Change Rule

Any future change to an approved B2A2B2 rule requires either an
already-authorized later owner or a superseding owner decision. The limits
register may record this decision but is not itself approving authority.
