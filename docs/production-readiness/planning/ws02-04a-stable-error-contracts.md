# WS02-04A Stable Backend Error Contracts

Status: implemented for repository source and current tests.

## Why WS02-04 Was Split

The WS02-04 inspection found that request limits, timeout budgets, retry policy,
rate controls, proxy identity, hosting-edge precedence, and stable application
errors are separate decision surfaces. FDN-04 approves the evidence-based method
for choosing operational values, but it does not approve specific numbers or
provider/runtime values.

WS02-04A therefore handles only the source-owned API-M12 error-contract slice.
API-M09, API-M10, and API-M11 may gain supporting evidence from this work, but
they are not closed by this slice.

## Scope

WS02-04A wires FastAPI exception handling to the EN-02 public error descriptor.
Application-owned error responses now include:

- top-level `detail` for existing frontend compatibility
- stable machine-readable `code`
- safe public `message`
- request correlation in the response body
- matching `X-Request-ID` response header
- safe validation `details` when field-level validation information is useful

The implementation preserves HTTP status codes and safe headers from existing
exceptions, including authentication and method headers.

## Backward Compatibility

The frontend currently reads top-level `detail`. WS02-04A keeps `detail` present
and compatible:

- string `detail` remains a string when safe
- dictionary `detail` remains a dictionary when safe
- validation `detail` remains a list
- unsafe submitted values and unsafe diagnostic strings are removed or replaced
  with the shared redaction marker

No frontend files were changed in this slice.

## EN-02 Preservation

The implementation reuses EN-02 correlation, public error descriptor, and
redaction primitives. It does not introduce a competing runtime error schema.

Incoming request IDs are accepted only when they are canonical UUIDv4
correlation identifiers. Invalid incoming values are not reflected. The active
correlation ID is returned in the public error body and `X-Request-ID` header.

Unexpected exceptions are logged with only safe redacted event context. Public
responses never include raw exception text, stack traces, SQL/database-driver
messages, provider payloads, filesystem paths, configuration values,
hostnames, credentials, tokens, cookies, or signed URLs.

## Middleware-Owned Limitations

Some responses are intentionally not converted into the JSON error envelope:

- invalid Host responses owned by Trusted Host middleware
- successful health responses
- docs HTML and OpenAPI schema responses
- redirects
- mounted static or file responses
- successful no-content responses
- any future streaming response class

The existing response-security-header middleware still applies the WS02-03
source-owned headers to application-owned API responses and middleware-owned
error responses where applicable.

## Historical Test Evidence

This section records the evidence used when WS02-04A was completed. After the
EN-01 testing reset, `backend/tests/shared/` is historical archive material, not
current trusted production-readiness evidence. Future trusted coverage for this
behavior must be re-derived from current authority under the EN-01 architecture.

At the time of this WS02 pass, tests under
`backend/tests/shared/api_errors/` covered:

- request-validation error shape
- malformed JSON error shape
- field-level validation information without submitted values
- HTTP exception normalization
- 404 and 405 behavior
- authentication and authorization behavior
- conflict behavior
- unexpected exception behavior
- correlation body/header consistency
- internal diagnostic leakage prevention
- preserved authentication and method headers
- CORS and response-security headers on representative errors
- Host validation remaining middleware-owned
- health, docs, OpenAPI, redirect, and no-content response shapes
- Stripe webhook raw-body handoff
- frontend-compatible top-level `detail`

Existing EN-02 observability, WS02-03 HTTP-security, WS02-01 settings,
authentication, webhook, and backend-suite tests remain relevant supporting
evidence.

## Explicit Deferrals

The following remain outside WS02-04A:

- numeric request limits
- pagination and collection-limit approval
- timeout values
- cancellation budgets
- provider retry policy
- rate-limit thresholds
- multi-instance limiter coordination
- trusted client-IP identity
- hosting-edge limits and error precedence
- provider and staging evidence
